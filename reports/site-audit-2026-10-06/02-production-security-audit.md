# Task 2 — Production security audit

**Report only. No security fixes, deployment, credential rotation, database cleanup, or IIS changes have been performed. Task 3 is deferred: the owner explicitly requested a stop after this report.**

Reviewed 2026-10-06 against source baseline `5d2c6f4`, IIS site/app pool `AkmlSqlSite`, and `https://akml.khamis.work`. Read alongside [Task 1](01-admin-functional-review.md).

## Executive assessment

The highest-priority defect is **trusting client-supplied forwarded headers**. Contrary to the source comments, clearing both trusted-proxy lists means trusting all senders. A caller can change its apparent IP and bypass login, consent and feedback limits. The published application reproduced this behavior locally with the same empty production proxy configuration.

Other confirmed concerns include production acceptance of TLS 1.0/1.1, ordinary local users being able to read the analytics database and hashing salt, spreadsheet formula injection, a public shared telemetry credential, insufficient intake limits, and gaps between privacy promises and collection/retention behavior. No administrator authentication bypass, SQL injection, executable XSS, or remote file traversal was demonstrated. No Critical finding was established.

The finding table contains **1 High, 11 Medium and 9 Low findings**. Severity reflects the demonstrated attack conditions; a hardening gap is not described as a demonstrated compromise.

## Scope, method and limits

- Read the entire Site request pipeline, public/admin routes, Razor pages, JavaScript, Markdown renderer, analytics/settings/feedback stores, telemetry receiver and desktop sender, deployment script, deployed `web.config`, effective site-specific IIS settings, filesystem ACLs and runtime modules. This covers the public Site application; the separate desktop Web SQL engine, other IIS websites, and the whole Windows host are not represented as fully audited.
- The deployed `AkmlSql.Site.dll` SHA-256 matched the local Release assembly. A copy of the published application ran on local HTTPS in Production mode with synthetic data, disposable credentials and a loopback SMTP sink. Authenticated actions and attack-shaped requests were tested **only there**.
- Production checks were low-volume GETs, TLS handshakes, configuration/ACL reads, and read-only database aggregates. Ordinary GETs can still create normal access/analytics records. No production login brute force, contact submission, download-count POST, deletion, load test, exploit chain or installer replacement was attempted.
- Production DNS and direct IIS loopback returned matching certificate/runtime behavior. Network probes originated on this server, so they do **not** establish behavior from an independent external network or every possible edge location. The web browsing service could not fetch the site; direct HTTPS probes with certificate verification succeeded.
- Existing Site tests: **877 passed**. Additional Chromium/request probes reproduced the findings below. This was not Task 3's Chrome/Edge/Firefox/mobile download acceptance suite.
- Current tracked text and `debug.log` received a redacted, pattern-based secret scan. Configuration values were inspected only as presence/work-factor/match facts. This was not an exhaustive Git-history, entropy, backup or organization-wide secret scan.
- No actual administrator password was available. Authenticated production actions, password strength, external alert delivery, backup restoration, Windows patch compliance, and production SMTP delivery remain unverified.

Evidence is kept outside public documentation in ignored `artifacts/site-audit-2026-10-06/`: `security-local.json`, `security-supplement.json`, `security-evidence.json`, `http-review.json`, `iis-review.json`, `data-acls.json`, `final-config-check.json`, `nuget-vulnerabilities.json`, `dependency-osv.json`, plus the Task 1 functional evidence. Local credentials and synthetic database contents are test artifacts, not deployable configuration. Do not publish the artifact directory.

## Injection, XSS, files and errors: checks without a demonstrated exploit

- **SQL:** SQLite uses raw command text, including concatenated internal table/column/predicate fragments. Traced these through `AnalyticsStore`, its Individuals/Insights partials, `SiteSettingsStore` and `FeedbackStore`; request values use parameters, while identifiers/predicates come from program constants. No Site stored procedures, user-provided SQL execution, or request-controlled SQL identifiers were found. The local quoted `country=' OR 1=1 --` filter returned a normal page without a SQL error. This one probe supplements source review; it is not proof against all SQLi.
- **Command/LDAP/header injection:** no request-driven process execution or LDAP operations were found in Site source. SMTP uses `MailMessage`/`MailAddress`, rejects CR/LF in reply addresses, builds subjects from a fixed category and ID, and sends plain text. A newline redirect value was rejected by the HTTP stack with 500 rather than injecting response headers; the tab normalization issue is SEC-14.
- **XSS:** ordinary Razor strings are encoded. Docs' deliberate `MarkupString` receives the repository Markdown renderer, with raw HTML disabled and link-scheme allowlisting (`Docs/MarkdownRenderer.cs:73`, `:360`). Search uses DOM `textContent`; result URLs come from the server-generated docs index. No user-controlled `eval`/HTML sink or executable stored/reflected/DOM-XSS path was established. Only passive raster doc assets are ingested; SVG docs are excluded. CSP blocks inline script. A compromised repository/deployment is a separate trust boundary.
- **Files:** there is no upload endpoint. Local encoded parent traversal, Windows backslash traversal and absolute Windows path probes all returned 404. `/web.config` and `/.git/config` returned 404 in production. `Path.GetFullPath` checks lexical containment; reparse-point escape resistance was not independently tested. The directory should remain writable only by the publishing identity (SEC-21).
- **AuthZ/IDOR:** all inventoried admin objects/actions are behind the same branch guard, and no alternate anonymous data API was found. A shared single-admin model has no role hierarchy to escalate through. This does not substitute for authenticated production testing or multi-user authorization tests if roles are added.
- **Errors:** production mode uses a generic exception page. Local exception probes did not expose stack traces/internal paths in HTTP responses. IIS is `DetailedLocalOnly` with existing response mode Auto, not an explicitly configured Custom-only policy; local detailed diagnostics remain possible. Production-like form/API status handling is still defective (SEC-15).

## Dependency and CVE review

`dotnet list src/AkmlSql.Site/AkmlSql.Site.csproj package --vulnerable --include-transitive --format json --no-restore` completed against NuGet.org with **no vulnerable packages reported**.
