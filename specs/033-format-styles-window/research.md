# Research: Format Styles Window Promotion (spec 033)

**Date**: 2026-07-22 | **Input**: `spec.md` + two parallel code-research sweeps (discovery: Options/window/SQL-Prompt-ref/menu; deep-dive: engine profiles/IPC, editor VM, schema builder, WPF idioms, test landscape). All file:line anchors verified on this date.

## R1 — ProfileGet returns the RAW stored file text, not a re-serialized profile

- **Decision**: `ProfileGet` (msg 34 → result 134) reads the resolved `.akmlstyle` file verbatim (`File.ReadAllText`) via a new `ProfileManager.TryReadRaw(name, out string json, out bool isBuiltIn)` that mirrors `Load()`'s custom-first probe.
- **Rationale**: `ProfileSerializer.Serialize` **stamps `Metadata.Modified = DateTime.UtcNow`** before writing (`ProfileSerializer.cs:27`), and `[JsonExtensionData]` exists only at the profile **root** (`FormattingProfile.cs:69-70`) — a Load→Serialize cycle bumps `modified`, re-indents, and silently drops unknown fields nested *inside* category objects. Raw text is the only faithful merge base for FR-008/FR-009.
- **Read-only flag**: derived from **which directory resolved** (built-in dir AND no custom shadow — the same rule `ProfileManager.Save` enforces at `ProfileManager.cs:103-106`). Never trust the JSON `isBuiltIn` field: the custom-load branch (`ProfileManager.cs:67-72`) doesn't reset it, so a custom file claiming `"isBuiltIn": true` would lie.
- **Alternatives rejected**: `Load()`+`Serialize()` (side effects above); shell reading profile files directly from disk (violates the process boundary; the shell doesn't know the engine's built-in dir).

## R2 — ProfileRename is a new engine operation, not shell-side compose

- **Decision**: `ProfileRename` (msg 35 → result 135). Engine-side algorithm: read raw custom file → update `metadata.name` (+`modified`) → atomic write to the new filename (temp + `File.Move` overwrite, the `Save` pattern at `ProfileManager.cs:114-117`) → delete the old file → **move the `<name>.source.json` sidecar** if present (import writes it at `FormatRequestHandler.cs:561-566`; losing it breaks lossless re-import).
- **Why not shell-side Duplicate+Delete**: `Duplicate` resets `Id`/`Created` and sets `BasedOn` (`ProfileManager.cs:186-206`) — a rename must preserve identity. A bare `File.Move` is also wrong: `List()` keys on `Metadata.Name` inside the JSON while `Load()` resolves by filename — the JSON name must be rewritten in the same operation.
- **Guards**: source must be custom (built-ins rejected); target collision checked `OrdinalIgnoreCase` against customs *and* built-ins (mirrors `List()`'s comparer and the import shadow-guard at `FormatRequestHandler.cs:549-557`); **case-only rename special-case** — if `SanitizeFileName(old)` equals `SanitizeFileName(new)` OrdinalIgnoreCase, skip the collision check (NTFS `File.Exists` would see the source as the "existing" target) and let `File.Move` do the case fix.
- **Active-profile follow-up is shell-side**: the engine cannot touch `AppSettings.Formatter.ActiveProfile` (shell-owned config; the engine has no set-active IPC and `ProfileInfo.IsActive` is never populated — `FormatRequestHandler.cs:269-292`). The VM updates config after a successful rename of the active style.

## R3 — Message/DTO layout follows the existing profile-message conventions

- **Decision**: `ProfileGetRequest{Name(0)}` / `ProfileGetResponse{Success(0), ErrorMessage(1), Name(2), ProfileJson(3), IsBuiltIn(4)}`; `ProfileRenameRequest{OldName(0), NewName(1)}` / `ProfileRenameResponse{Success(0), ErrorMessage(1), NewName(2)}` — one class per file in `src/AkmlSql.Core/Ipc/Messages/`, `[MessagePackObject]` + int `[Key(n)]`, exactly like `DuplicateProfileRequest/Response`. Handlers: thin `IRpcRequestHandler<TReq,TResp>` adapters in `Handlers/Formatting/FormattingHandlers.cs` delegating to `FormatRequestHandler`, registered in `EngineHandlerRegistry.cs:160-166`. Request IDs 34/35 and result IDs 134/135 verified free in `RpcMessage.cs`.
- **Also fix while there**: `HandleProfileDelete` discards `Delete()`'s bool (`FormatRequestHandler.cs:309-321`) so deleting a nonexistent profile reports `Success=true` — return the real result. Add the missing 1 MB `ProfileJson` size cap to `HandleProfileSave` (import has one at `FormatRequestHandler.cs:504-512`; save has none).

## R4 — AllowedEnumValues/Description/Min/Max come from a new `[SettingMeta]` attribute (there are NO C# enums)

- **Finding that changes the spec's mental model**: the profile POCOs contain **zero C# enum types** — every enum-like option is a plain `string` with allowed values documented only in XML doc comments (`ClassifyType` maps every string to `"Enum"`, `FormatSettingSchema.cs:211`). Enum reflection is impossible.
- **Decision**: one custom attribute in `AkmlSql.Formatting/Profiles`: `[SettingMeta(Description = "...", AllowedValues = new[]{...}, Min = n, Max = m)]`, applied to all ~178 settable properties across the 18 POCOs (~60 enum-like strings get `AllowedValues`; the 14 ranged ints get `Min`/`Max`; everything gets `Description`). `BuildDefault()`'s inner loop reads it with one `GetCustomAttribute<SettingMeta>()` call, mirroring the existing `JsonPropertyNameAttribute` pattern (`FormatSettingSchema.cs:70/89`).
- **Why not BCL attributes** (`DescriptionAttribute`/`RangeAttribute`/`AllowedValuesAttribute`): available on net10 with no package change, but `AllowedValuesAttribute` stores `object[]` (validation-oriented), `RangeAttribute` boxes, and three attributes per property is noisier than one; a bespoke typed attribute is trim-local and matches the DTO exactly.
- **Trimming is a non-issue (spec premise corrected)**: the engine has `PublishTrimmed=false` (`AkmlSql.Engine.csproj:17`); the trimmed consumers (`akmlsql-format` CLI, Blazor WASM) never call `FormatSettingSchema`.
- **Value-casing policy**: profile JSON stores string values verbatim, mixed-case (`"UPPERCASE"`, `"AsIs"`, `"trailing"`) with no `JsonStringEnumConverter` — `AllowedValues` entries are the **exact stored spellings**; the ComboBox writes the selected string verbatim; any comparison is OrdinalIgnoreCase for matching but always persists the canonical spelling from the attribute.

## R5 — Schema v2 is population + a version-bump literal; zero wire changes

- The v2 fields **already exist, unpopulated**: `FormatSettingGroup.ParentId` (`FormatSettingSchema.cs:261`), `FormatSetting.AllowedEnumValues/Min/Max/Description` (`:273-278`). The schema crosses the pipe as a **JSON string** inside `StyleEditorSchemaResponse.SchemaJson` (`[Key(1)]`, deliberate netstandard2.0 decoupling per its doc comment) — enriching it needs **zero MessagePack changes**.
- `SchemaVersion` is an inline literal `1` at `FormatSettingSchema.cs:56` → bump to `2`. The engine caches via `FormatSettingSchema.Default` (Lazy) and short-circuits `Cached=true` when `ClientSchemaVersion` matches (`FormatRequestHandler.cs:453-461`); the shell caches version+JSON in process-lifetime statics (`FormatStylesEditorViewModel.cs:42-43`) — the bump invalidates both automatically. Do **not** conflate with `ProfileSerializer.CurrentSchemaVersion` (the `.akmlstyle` file version, stays 1).
- **Category representation**: categories are emitted **only as `ParentId` values** on the 18 group rows (`global` / `statements` / `clauses` / `expressions` / `other`); the shell maps id → display name with a fallback (unknown/missing ParentId → "Other"). Emitting categories as extra parentless group rows was rejected: an un-updated shell would render 5 empty flat nodes. The spec's category assignment covers all 18 groups exactly (verified 4+5+2+5+2).
- **Id stability is load-bearing**: `SqlPromptKey`/`Status` resolution keys on the exact setting-id format `"{groupId}.{jsonName}"` via the 38-entry `ExplicitKeyMap` (`FormatSettingSchema.cs:125-167`) — categories go in `ParentId` only; group ids and setting ids stay byte-identical.
- **InsertStatements wart**: `InsertStatementsOptions.Columns/Values` are class-typed (`InsertParenOptions`), so today their 6 real sub-settings are invisible ("Other" blobs). **Decision: flatten** to multi-segment ids (`insertStatements.columns.parenthesisStyle`, …). Consequence: profile-JSON construction must nest by **all** dot segments (the current `BuildProfileJson` splits on the first dot only, `FormatStylesEditorViewModel.cs:298-299`) — the new merge writer handles arbitrary depth. These new ids get `ExplicitKeyMap` entries alongside (Redgate keys exist in the importer's insertStatements section).

## R6 — Save is a shell-side JsonNode merge over the raw loaded JSON

- **Decision**: the VM retains the `ProfileGet` raw JSON as the merge base; Save parses it with `System.Text.Json.Nodes` (`JsonNode`), overlays each edited working value by its full dotted path (creating nested `JsonObject`s as needed), and sends the result to the existing `ProfileSave` (msg 15). `HandleProfileSave` derives the persisted identity from the JSON's `metadata.name` (`FormatRequestHandler.cs:294-300`) — the merge base already carries the correct metadata, which is exactly why merge (not synthesize) is required.
- **Feasibility confirmed**: STJ **9.*** is referenced for Core's netstandard2.0 target (`AkmlSql.Core.csproj:18-21` — CLAUDE.md's "8.x" note is stale) and `System.Text.Json.Nodes` is already used in this VM on net472 (`FormatStylesEditorViewModel.cs:10, 292-311`). No new package.
- The merge is implemented as a **pure internal static** (e.g. `ProfileJsonMerger.Merge(baseJson, workingValues)`) so it is unit-testable without any IPC.

## R7 — The VM gets an injectable IPC seam (prerequisite for every VM test)

- **Finding**: the VM reaches the pipe through the static `EngineLifecycle.Manager?.Client` at six call sites (`FormatStylesEditorViewModel.cs:357,436,490,527,579,624`); `EngineLifecycle.Manager` has no setter and `Client` is the concrete `PipeRpcClient` — **no fake-IPC is possible today**, and zero tests reference this VM.
- **Decision**: introduce a small delegate/interface seam in the VM (default = current static lookup; tests inject a fake returning canned responses per message type). Load-on-select, dirty flow, save/rename/delete flows, and read-only guards all become headlessly testable in `AkmlSql.Shell.Shared.Tests` (which compiles Shell.Shared sources via the `.projitems` import, so internals are directly instantiable — `AkmlSql.Shell.Shared.Tests.csproj:55`).

## R8 — Selection/dirty hook points and threading discipline

- Selection lands in `_styleList.SelectionChanged` → `vm.SelectedProfileName` setter (`FormatStylesEditorWindow.cs:252-258`, VM:73-77) — the setter is the documented hook for load-on-select; dirty-guarding must intercept **before** the setter overwrites state (prompt Save/Discard/Cancel, and on Cancel restore the previous list selection without re-triggering).
- Anything touching bound collections/properties follows the existing `SwitchToMainThreadAsync` discipline (`LoadProfilesAsync`, VM:598-613). Preview pipeline (100 ms debounce + CTS + sequence supersession, VM:328-388) is untouched; load-on-select re-seeds working values then calls `QueuePreviewAsync()`.
- Dead code to remove while in the file: the `SelectedItemChanged` handler at window:637-644 (never receives a `FormatSettingNode`); the duplicated `UpdateStatus` (window:1190-1193, identical to `SetStatus`).

## R9 — WPF idioms: themed combos, sectioned list, sub-dialogs, broken template

- **Enum ComboBoxes**: build with **plain-string items** and call `ComboBoxTheming.Apply(combo)` (`Ui/Theme/ComboBoxTheming.cs:34` — the parameterless-theme overload; HC no-op built in). Hard rule from the helper: string items only (UIElement content → blurry VisualBrush + broken type-ahead). Consumer pattern to copy: `RowFactory.AddDropdown` → `StyleComboBox` (`Dialogs/Pages/RowFactory.cs:217, 405`).
- **Style-list sections + ✔ active + lock glyph**: replace the broken XAML-string DataTemplate — it references `{StaticResource BoolToVisibilityConverter}` that is **never registered** (`FormatStylesEditorWindow.cs:567`; the only such converter is a private nested class in `History/HistoryToolWindowControl.cs:2496`), so `XamlReader` always throws and the fallback drops the lock glyph. Decision: build the item template **in code** (no XAML string), rendering section headers via `CollectionViewSource` grouping on a new `StyleListItem.IsReadOnly`-derived section, ✔ from a new `IsActive` flag (computed shell-side from `AppSettings.Formatter.ActiveProfile` — it is *not* on the wire), and the lock glyph from `IsReadOnly`. Context menu per item (Set Active / Copy / Rename / Delete / Export).
- **New-based-on + Rename prompts**: small `ThemeAwareWindow` subclasses (`Ui/Theme/ThemeAwareWindow.cs:16-50`) with the accepted-flag closure shape of `SettingsWindow.ShowRuleEditor` (`Dialogs/SettingsWindow.cs:1917-2019`) and **`Owner = <styles window>`** per the nested-modal rule documented on `ImportSummaryDialog` (`Formatting/ImportSummaryDialog.cs:19-31`).
- Frozen brushes + `Typography.UiFont/MonoFont` statics + `ThemeTokens` resource references, per CLAUDE.md and the window's existing conventions.

## R10 — Options page: launch button + refresh, and the ActiveProfile clobber fix

- Button lands after the Active-style dropdown/status-bar rows (`FormattingPage.cs:26-34`) via `RowFactory.AddButton` (`RowFactory.cs:135-163`); "Behavior" header via `AddGroupHeader` replacing the current "Triggers"/"Safety & Validation" split (or as parent header above both — final layout in tasks).
- `FormatStylesEditorWindow.Launch()` is modal (`ShowDialog`), so the refresh is synchronous after return: re-read `ConfigManager.Load().Formatter.ActiveProfile`, re-seed the combo, re-run `PopulateProfilesAsync(active)` (`FormattingPage.cs:150-176`).
- **Clobber mechanism confirmed**: `FormattingControls.Save` writes `ActiveProfile = SelectedName()` unconditionally (`FormattingPage.cs:132-136`) and Options OK persists the whole snapshot (`OptionsCommand.cs:57-58`) — without the post-close refresh, OK'ing Options reverts a Set-Active done inside the window. The refresh (repopulate AND re-select the fresh on-disk name) is the fix; no save-path change needed.
