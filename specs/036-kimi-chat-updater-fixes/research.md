# Research: Kimi provider, schema-aware chat, Options hover, update channel (spec 036)

**Date**: 2026-09-02 | **Input**: `spec.md` + a direct read of every touched file. All `file:line` anchors verified on this date against branch `036-kimi-chat-updater-fixes` (base commit `054b5db`).

---

## R1 — Every AI request in the shell fabricates its session id, so no AI feature has ever had schema access

- **Finding**: `AiChatPanel.SendMessageAsync` sets `SessionId = Guid.NewGuid().ToString("N")` (`src/AkmlSql.Shell.Shared/Ai/AiChatPanel.cs:236`). The engine's `AiChatHandler` resolves the connection with `ctx.Sessions.GetSession(sid)` and returns `(null, null)` when the lookup misses or the session is not connected (`src/AkmlSql.Engine/Handlers/Ai/AiChatHandler.cs:36-39`). `SchemaContextBuilder.BuildAsync` then returns an empty context (`src/AkmlSql.AI/Context/SchemaContextBuilder.cs:64-68`) and `SchemaContextFormatter.Format` emits the literal string `"(No schema objects available)"` (`src/AkmlSql.AI/Context/SchemaContextFormatter.cs:27-29`), which is what the model receives as its entire view of the database.
- **The same defect exists in two more places**: `GhostTextAdornment.cs:134` and `TextToSqlCommand.ExtractPromptFromEditor` (`src/AkmlSql.Shell.Shared/Commands/TextToSqlCommand.cs:236`, with a second fabrication in the catch at `:137`). The command-based features (`AiExplainCommand`, `AiFixCommand`, `AiOptimizeCommand`, `AiIndexAnalysisCommand`) pass a `sessionId` variable — those need auditing, not assuming, because `TextToSqlCommand` proves passing a variable is no guarantee the variable holds a *real* id.
- **Decision**: resolve the real id from the active editor buffer's `AkmlSqlSessionId` property, which `TextViewCreationListener` sets at `src/AkmlSql.Shell.Shared/Editor/TextViewCreationListener.cs:37`.
- **Rationale**: `ConnectionWiringHelper.SendConnectionChangedAsync` sends `ConnectionInfo { SessionId = sessionId, ConnectionString, DatabaseName }` over `MessageTypes.ConnectionChanged` (`src/AkmlSql.Shell.Shared/Editor/ConnectionWiringHelper.cs:286-303`), and `SessionManager.UpdateSession` creates the session with `IsConnected = true` keyed on exactly that id (`src/AkmlSql.Engine/Server/SessionManager.cs:14-40`). So the engine already holds a live, connected session under the buffer's id — the chat simply has to use it.
- **Alternatives rejected**: a chat-owned session registered via its own `ConnectionChanged` (duplicates connection detection, and the chat has no connection of its own — it must follow the editor); passing the connection string in the chat request (puts credentials on the wire for no reason and bypasses the cache identity).

## R2 — The tool window has no buffer, so it must resolve the active editor at send time

- **Decision**: reuse `RefactorCommandHelper.TryGetActiveEditor()` (`src/AkmlSql.Shell.Shared/Refactoring/RefactorCommandHelper.cs:45-91`). It calls `IVsTextManager.GetActiveView`, adapts to a `IWpfTextView`, and reads `AkmlSqlSessionId` off the buffer, returning null when there is no managed view.
- **Rationale**: three resolvers for the same property already exist (`RefactorCommandHelper`, `RefreshCacheCommand.TryGetActiveSessionId` at `src/AkmlSql.Shell.Shared/Commands/RefreshCacheCommand.cs:225-276`, and the inline reads in `CompletionPopupProvider`/`QuickInfoSource`/`SignatureHelpSource`). Constitution principle V forbids adding a fourth. `RefactorCommandHelper` is the right one because it is already public, already `ThreadHelper.ThrowIfNotOnUIThread()`-guarded, and already returns the session id as a first-class field.
- **Caveat to fix**: `TryGetActiveEditor` falls back to `Guid.NewGuid().ToString("N")` when the property is missing (`:70-74`), with the comment "pure-text ops still work without a real session". That fallback is correct for refactoring but **wrong for AI** — a fabricated id is exactly the bug in R1. AI callers must distinguish "no real session" from "here is an id", so the AI path needs the null/empty case surfaced rather than papered over (add a `HasRealSession` flag or a separate accessor; do not change the existing fallback, which refactoring depends on).
- **FR-027 consequence**: the panel must re-resolve when the active window changes, not cache once at construction. `AiChatPanel.SetDatabaseContext(string)` already exists (`AiChatPanel.cs:185-192`) and is called by nothing — that is the hook to drive.

## R3 — The AI provider connection test already exists end-to-end; only the shell caller is missing

- **Finding**: `MessageTypes.AiProviderTest = 77` and `AiProviderTestResult = 177` are defined (`src/AkmlSql.Core/Ipc/RpcMessage.cs:223,263`); `AiProviderTestRequest{Provider(0), ApiKey(1), Endpoint(2), Model(3)}` and `AiProviderTestResponse{Success(0), ModelName(1), ProviderVersion(2), ErrorMessage(3), LatencyMs(4)}` exist in `src/AkmlSql.Core/Ipc/Messages/`; `AiProviderTestHandler` builds temporary `AiSettings`, calls `AiProviderFactory.Create`, sends the prompt `"Say hello in one sentence."`, and maps exceptions to friendly text (`src/AkmlSql.Engine/Ai/AiProviderTestHandler.cs:36-140`); it is registered at `src/AkmlSql.Engine/EngineHandlerRegistry.cs:78`.
- **A repo-wide grep for `AiProviderTest` returns no hit under `src/AkmlSql.Shell.Shared/`.** Nothing ever sends message 77.
- **Decision**: FR-009 is implemented by adding a "Test connection" button to `AiAssistancePage` that sends the existing message with the *current dialog field values* (not the saved settings, so the user can test before saving). No new message type, no DTO change.
- **Rationale**: Constitution V — extend, do not duplicate. The handler's error mapping (`InvalidOperationException` → message verbatim, `HttpRequestException` → HTTP text, else generic) is already most of FR-014's taxonomy; the remaining causes (quota/rate-limit, timeout) are refinements to that existing `switch` at `AiProviderTestHandler.cs:122-129`.
- **Alternatives rejected**: a new `AiProviderTestV2` pair (gratuitous); testing client-side in the shell (net472 has no provider SDK, and it would violate process isolation).

## R4 — AI API keys are stored in plaintext; the fix is to promote the engine's existing protector into Core

- **Finding**: `AiAssistancePage.Save` writes `settings.Ai.ApiKey = _apiKey.Text ?? string.Empty` (`src/AkmlSql.Shell.Shared/Dialogs/Pages/AiAssistancePage.cs:282`) and `Load` reads it back raw (`:237`). Nothing on the shell path encrypts. Meanwhile `AiProviderFactory.DecryptApiKey` runs the value through the `KeyDecryptor` hook (`src/AkmlSql.AI/Providers/AiProviderFactory.cs`), which `EngineHost` points at `CredentialManager.Decrypt` (`src/AkmlSql.Engine/EngineHost.cs:52-53`) — and that function returns the input unchanged when it lacks the `dpapi:` prefix (`src/AkmlSql.Engine/Ai/Security/CredentialManager.cs:60-70`). So plaintext keys work, and that is why nobody noticed.
- **Contrast**: SQL passwords *are* DPAPI-wrapped, by `SqlCredentialStore` in `AkmlSql.Core` (`src/AkmlSql.Core/Config/SqlCredentialStore.cs:201-222`).
- **Decision**: add `AkmlSql.Core/Config/ApiKeyProtector.cs` with `Protect`/`Unprotect`/`IsProtected`, carrying the **exact** existing entropy `SHA256(UTF8("AkmlSql-ApiKey-v1"))` from `CredentialManager.cs:23`, and reduce `CredentialManager` to a forwarder so the engine's call sites and any existing tests keep working unchanged.
- **Rationale**: `System.Security.Cryptography.ProtectedData` is already a `PackageReference` in `AkmlSql.Core.csproj:26` and the project multi-targets `netstandard2.0;net10.0` (`:4`), so one implementation serves both the net472 shell and the net10 engine. The engine's `CredentialManager` cannot be referenced by the shell (wrong TFM), and copying the algorithm into the shell would be the "parallel mechanism" principle V forbids.
- **Critical constraint**: the entropy differs from `SqlCredentialStore`'s (`ComputeEntropy()` at `SqlCredentialStore.cs:33`). Using the wrong one makes every already-stored key undecryptable. Preserve `"AkmlSql-ApiKey-v1"` byte-for-byte.
- **Migration**: reads stay backward-compatible for free (plaintext passthrough). The first save after this change upgrades the stored value in place. No migration step, no user action.
- **Alternatives rejected**: leaving keys plaintext (fails FR-008); a new AES-GCM scheme (a second mechanism, and DPAPI is already the house standard for machine-local secrets); encrypting inside `ConfigManager` generically (would silently re-encrypt unrelated fields and break config round-tripping).

## R5 — Kimi is an OpenAI-compatible provider, so the factory needs one case, not a new adapter

- **Decision**: add `"kimi" => CreateOpenAiClient(apiKey, settings.Model, settings.Endpoint ?? DefaultKimiEndpoint)` to the switch in `AiProviderFactory.Create` (`src/AkmlSql.AI/Providers/AiProviderFactory.cs`, alongside the existing `lmstudio`/`custom` cases which already take that shape).
- **Rationale**: `CreateOpenAiClient` already handles the "custom endpoint + API key" configuration, constructing `OpenAIClientOptions { Endpoint }` with an `ApiKeyCredential`. Gemini needed a bespoke `GeminiChatClientAdapter` because its wire format differs; Kimi's does not.
- **Nuance**: the existing custom-endpoint branch deliberately skips `RequireModelFamily` because "custom endpoints legitimately serve foreign model ids". Kimi is a *named first-party* provider, so it must be family-guarded like Anthropic/OpenAI/Gemini — meaning the Kimi case cannot simply fall through to the generic custom branch; it needs its own case that validates first, then delegates.
- **Defaults** (see `contracts/kimi-provider.md` for the normative values): a rolling model alias rather than a pinned version, following the precedent set for Gemini — `DefaultModelFor` uses `"gemini-flash-latest"` with the comment "pinned Gemini names rot" (`src/AkmlSql.Core/Config/AiModelFamily.cs:57-63`). Endpoint defaults to the international Moonshot base URL; the mainland-China service is reached by overriding the endpoint field, per the spec's Assumptions.
- **Alternatives rejected**: telling the user to pick "Custom" and type the endpoint (fails FR-006's "named, selectable provider" and the 2-minute SC-002 target); a dedicated adapter class (unnecessary — no wire-format difference to absorb).

## R6 — The relevance filter's zero-match fallback is the real cause of thin schema context, not the object cap

- **Finding**: `FilterByRelevance` returns all objects only when `matched.Count == 0` (`src/AkmlSql.AI/Context/SchemaContextBuilder.cs:138`). `TokenizePrompt` keeps every token of length ≥ 2 that is not in the SQL-keyword stop list (`:145-160`), and `IsObjectRelevant` matches with `Contains` (substring, not word) against object and column names (`:186-200`). So "what tables do **my** orders **do**" yields tokens like `my`/`do` that substring-match incidentally — producing a non-empty `matched` set of one or two irrelevant objects and thereby *suppressing* the fallback that would have sent the whole inventory.
- **The stop list already contains** `the/for/this/that/how/what/show/me/get/find/list/write/query/can/you/help` (`:167-172`) — evidence the author knew about noise tokens but could not enumerate them all. Enumeration is the wrong fix.
- **Decision**: invert the assembly. Always include the full object inventory at detail level 1 (names, types, row counts — cheap), then *add* level-3 detail (columns, PKs, indexes, FK relationships) for objects the prompt actually names, all inside one explicit budget. Relevance stops being a filter that can remove things and becomes a rule that promotes detail.
- **Rationale**: this satisfies FR-024 ("general question → full inventory") and FR-025 ("narrowing may add detail, must not remove inventory") simultaneously, and it is strictly cheaper than raising the detail level for everything. `SchemaContextFormatter` already implements all four levels (`src/AkmlSql.AI/Context/SchemaContextFormatter.cs:31-38`), so no new rendering is needed.
- **Second finding**: `AiChatHandler` hardcodes `compressionLevel: 2` (`src/AkmlSql.Engine/Handlers/Ai/AiChatHandler.cs:42-43`), and level 2 omits primary keys, indexes and FK relationship lines — which FR-023 requires. The same hardcoded `2` appears in the explain/fix/optimize/index-analysis/text-to-SQL/ghost-text handlers. Ghost text should stay lean (latency-critical); the rest need the richer context.
- **Third finding**: `maxObjects` defaults to 500 (`SchemaContextBuilder.cs:54`) and the cap is applied by `expandedSet.Take(maxObjects)` — an *arbitrary* truncation with no signal to the model or the user. FR-026 requires the truncation be explicit.
- **Alternatives rejected**: growing the stop list (whack-a-mole, and "do" is a legitimate column name somewhere); requiring a minimum match score (still deletes inventory on general questions); sending everything at level 3 always (token cost on a 500-object database, and misses the latency goal).

## R7 — The Options nav hover bug is WPF trigger ordering, and it only bites the selected item

- **Finding**: in `SettingsWindow.BuildNavTree` the selected trigger sets **both** `Background` (`_theme.Selected`) and `Foreground` (`_theme.SelectedText`) at `src/AkmlSql.Shell.Shared/Dialogs/SettingsWindow.cs:415-418`; the mouse-over trigger immediately after sets **only** `Background` (`_theme.TreeHover`) at `:420-422`. When both conditions hold, WPF applies the later trigger's setter for the property they share, so the item paints `TreeHover` background with `SelectedText` foreground.
- **Concretely**: `SelectedText` maps to `ThemeTokens.TextOnAccent` and `TreeHover` maps to `ThemeTokens.SurfaceHover` (`src/AkmlSql.Shell.Shared/Ui/Theme/PageTheme.cs:80-88`). In the Light palette `SurfaceHover` is `#F1F5F9` (`src/AkmlSql.Shell.Shared/Ui/Theme/ThemePalette.cs:84`) — near-white — while `TextOnAccent` is white. **White on near-white**: exactly the reported symptom.
- **Decision**: pair a foreground with every background in hover state — add a `Foreground` setter to the mouse-over trigger, and add a `MultiTrigger` for selected-and-hovered that keeps the selected pair intact. Ordering fixes alone are insufficient because they only move the problem.
- **Second site**: `BuildSearchResultsPopup` adds its hover trigger *before* its selected trigger (`:735-742`), so it does not currently show the bug — but it also never pairs a foreground with `TreeHover`, leaving it one palette change away. FR-003 covers it; fix both the same way.
- **High Contrast constraint**: `BuildHighContrast` maps `SurfaceHover` to `SystemColors.HighlightBrush` and `TextOnAccent` to `SystemColors.HighlightTextBrush` (`ThemePalette.cs:289,300`), so the fix must derive the paired foreground from tokens, never from a literal. FR-004's sweep must cover this palette.
- **Test precedent**: `WindowChromeTests` already reflects over the nav style to pull the `ForegroundProperty` setter (`tests/AkmlSql.Shell.Shared.Tests/WindowChromeTests.cs:355-362`, `GetForegroundFromStyle`) and asserts per-theme visibility with `[StaFact]`. The FR-004 contrast sweep extends that helper to walk triggers as well as base setters.
- **Alternatives rejected**: reordering the triggers only (a selected item would then paint the accent background under the pointer, losing the hover affordance entirely); hardcoding a safe foreground (violates the token rule in `CLAUDE.md`); an `IValueConverter` computing contrast at render time (over-engineered; the palette is known at build time).

## R8 — Provider display names are saved in a form the factory rejects for two existing providers

- **Finding**: `AiAssistancePage.Save` maps index → `"AzureOpenAI"` / `"LMStudio"` (`src/AkmlSql.Shell.Shared/Dialogs/Pages/AiAssistancePage.cs:270-279`), but `AiProviderFactory.Create` switches on the lowercased values `"azure"` and `"lmstudio"`. `"azureopenai"` matches no case and falls to the `_ =>` arm that throws *"Unknown AI provider"*. `Load` maps `"azureopenai"` → index 3 (`:225-235`), so the round-trip through the dialog looks fine while every AI call fails.
- **Decision**: introduce one canonical id per provider and normalise on read. Add an alias table so `azureopenai`→`azure` and `lmstudio`→`lmstudio` resolve regardless of stored casing or spelling, and make `Save` write the canonical id. Existing configs keep working because the alias table accepts the old spellings.
- **Rationale**: FR-013 requires that every list entry the UI can save is accepted by the backend. Adding Kimi touches this exact mapping, so fixing it here is in-scope and cheap; leaving it would mean shipping a third entry into a mapping known to be broken.
- **Alternatives rejected**: changing only the `Save` strings (breaks every already-saved config silently); adding `"azureopenai"` as a duplicate switch case (encodes the typo permanently and does not help the next provider).

## R9 — Chat bubbles cannot be selected, which is why partial copy is impossible

- **Finding**: `CreateMessageBubble` renders the message into a `TextBlock` (`src/AkmlSql.Shell.Shared/Ai/AiChatPanel.cs:341-349`). `TextBlock` has no selection support. The per-message copy button (`:351-366`, handler at `:401`) and the per-SQL-block buttons built from `response.CodeActions` (`:299-323`) both already work and must be preserved — `AiChatPanelCopyButtonTests` covers them.
- **Decision**: swap the `TextBlock` for a read-only, borderless, transparent `TextBox` with `IsReadOnly = true`, `TextWrapping = Wrap`, and `BorderThickness = 0` — the standard WPF way to get selectable static text without a `RichTextBox`'s weight.
- **Rationale**: preserves the existing layout `Grid` (text in column 0, copy button in column 1), keeps `SetResourceReference` theming working on `Foreground`, and costs nothing at render time. A `RichTextBox` would be needed only if FR required formatted rendering, which the spec explicitly puts out of scope.
- **Watch item**: a read-only `TextBox` still takes focus and handles `Enter`. The panel binds `Enter` to send on the *input* box (`OnInputKeyDown`, `:193-201`); confirm the bubble's key handling does not swallow anything, and that `Background = Transparent` survives the theme swap.
- **Copy-conversation (FR-018)**: build from the existing `_history` list of `ChatTurnDto` (`:242-248`) — it already holds role and content for every turn, so the action is a format-and-set, with no new state.

## R10 — The update check has never worked in any shipped build

- **Finding**: `Constants.UpdateManifestUrl = "https://updates.akmlsql.com/manifest.json"` (`src/AkmlSql.Core/Constants.cs:24`). Nothing in the repository publishes to that host; `scripts/deploy-site-iis.ps1` writes only `src/AkmlSql.Site/wwwroot/releases.json`. `tests/AkmlSql.Core.Tests/ConstantsTests.cs:45` asserts the dead string, so the test suite has been locking the bug in.
- **What exists instead**: the site is live at `https://akml.khamis.work` (`Site:BaseUrl`, `src/AkmlSql.Site/appsettings.json:10`) and serves `releases.json` from `wwwroot`, with entries carrying `version`, `releasedAt`, `downloadUrl`, `sha256Hash`, `releaseNotesUrl`, `notesSummary`, `minimumOsVersion` and — since commit `054b5db` — `cdnUrl` pointing at the GitHub release asset (`src/AkmlSql.Site/Releases/Release.cs:11-42`).
- **Decision**: point the check at the site, and have `scripts/deploy-site-iis.ps1` emit the updater's manifest from the **same in-memory entry object** it already builds for `releases.json` (`scripts/deploy-site-iis.ps1:158-172`), so the two cannot drift.
- **Rationale**: FR-036 demands the download page and the update channel agree, produced by the release process rather than by hand. The script already computes the version from the EXE's `VersionInfo.FileVersion`, the SHA-256 via `Get-FileHash`, and the CDN URL from the `gh release` result — every field the manifest needs is already in hand at that point.
- **Shape mismatch to resolve**: `UpdateManifest` is a single latest release (`src/AkmlSql.Core/Update/UpdateManifest.cs`) while `releases.json` is a list, newest-first. Emitting a separate small manifest keeps the updater's parsing trivial and avoids teaching a net10 single-file CLI to sort a growing list. See `contracts/update-manifest.md`.
- **Alternatives rejected**: standing up `updates.akmlsql.com` (new infrastructure, explicitly out of scope); pointing the updater at the GitHub Releases API (rate-limited for anonymous callers, and FR-034 requires anonymous success); having the updater parse `releases.json` directly (works, but couples the CLI to the site's growing manifest and its `IsLatest`/availability semantics).

## R11 — The updater only checks; download, verify and launch are new, and belong in the updater process

- **Finding**: `AkmlSql.Updater/Program.cs` accepts exactly one argument, `--check` (`:29-33`), fetches the manifest, compares with `IsNewerVersion` (`:121-131`, which strips SemVer pre-release tags before `new Version(...)`), and on success writes `update-available.json` atomically (temp + `File.Move(overwrite: true)`, `:75-78`). It never downloads. `UpdateResult.Sha256Hash` is carried all the way through and then used by nobody.
- **Shell side**: `CheckUpdateCommand` reads the result file and, if `IsValidHttpsUrl(result.DownloadUrl)`, opens the URL with `Process.Start` — i.e. hands the user to a browser (`src/AkmlSql.Shell.Shared/Commands/CheckUpdateCommand.cs:56-70`).
- **Decision**: add `--download` to the updater. It re-reads the result file, downloads to `%AppData%\AKML SQL\cache\`, computes SHA-256, compares against the manifest value, deletes the file and exits non-zero on mismatch, and on success records the verified absolute path back into `update-available.json`. The shell then shows one confirmation naming the hosts that must close and launches that verified local path.
- **Rationale**: Constitution principle I. A ~72 MB download inside the SSMS process is precisely the host-safety risk the out-of-process split exists to avoid. The updater is already a separate, self-contained, single-file process launched fire-and-forget by `UpdateLauncher.LaunchUpdater()` (`src/AkmlSql.Shell.Shared/Update/UpdateLauncher.cs:41-60`), which passes `--check` today and can pass `--download` tomorrow with no new plumbing.
- **Throttle (FR-042)**: `LaunchIfDue` returns early when `elapsed.TotalHours < Constants.UpdateCheckIntervalHours` (`UpdateLauncher.cs:22-30`). The manual command must call `LaunchUpdater()` directly, bypassing `LaunchIfDue`. Note `LaunchUpdater` is already public and already separate from the throttled path — the split was anticipated.
- **Confirmation dialog**: follow the FR-005 safety-dialog convention from `CLAUDE.md` — Cancel is `IsCancel = true` and holds initial focus; the proceed button is not the default. Reference implementation: `src/AkmlSql.Shell.Shared/Safety/SafetyWarningDialog.cs`.
- **Alternatives rejected**: downloading in the shell on a background thread (still in-process; a hung socket or a thread-pool starvation stalls the host); a Windows service or scheduled task (new infrastructure); silent `/VERYSILENT` install (rejected by the user on 2026-09-02 — it would close SSMS without warning and hide failures; that switch stays reserved for the documented unattended-deployment path in `doc/deployment.md`).

## R12 — The installer already supports in-place upgrade; FR-043 is verification, not construction

- **Finding**: `AkmlSqlSetup.iss` pins `AppId={{F7E8A9B0-C1D2-E3F4-A5B6-C7D8E9F0A1B2}` with the comment "Inno Setup uses this to detect existing installations … handles version bumps automatically as long as AppId remains the same" (`src/AkmlSql.Installer/AkmlSqlSetup.iss:74-79`). `CloseApplications=yes` with `CloseApplicationsFilter=Ssms.exe,devenv.exe` (`:126-127`) covers running hosts. `VersionInfoVersion={#MyAppVersion}` stamps the EXE (`:94`) — which is what the deploy script reads back via `VersionInfo.FileVersion`, closing the version loop.
- **Preservation risk to check, not assume**: the post-install step writes `config.json` only when absent (per `CLAUDE.md`), so settings survive — but query history, snippets, format styles and `sql-credentials.json` live under `%AppData%\AKML SQL\` and are not installer-managed at all, which is *why* they survive. FR-043 requires proving that, on a populated installation, rather than reasoning about it.
- **Decision**: no installer changes. FR-043/FR-044 are quickstart verification steps; FR-045 (three-way version agreement) becomes an assertion in the clean-machine run.
- **FR-046 sequencing**: this is the one requirement that cannot be closed on the development machine. It needs the previous published build installed on a clean Windows box and a real newer release published. Everything else in slice E is verifiable locally against a staged manifest served from the dev site. Evidence goes in `doc/progress.md` per the constitution's documentation-currency rule.
