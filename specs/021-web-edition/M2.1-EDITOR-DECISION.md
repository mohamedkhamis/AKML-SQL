# M2.1 — Editor decision (spec 021 T031)

**Decision: CodeMirror 6.**

## Why not Monaco

Monaco is the editor that powers VS Code, and its keybinding fidelity / IntelliSense affordances would be the natural choice given the IDE-plugin parity goal. We did not pick it because:

| Concern | Monaco | CodeMirror 6 |
|---------|--------|--------------|
| Minified bundle (editor + worker, gzip) | ~1.3 MB | ~150-200 KB for `@codemirror/state` + `@codemirror/view` + `@codemirror/lang-sql` |
| Worker / blob URL setup | Required — Monaco needs `MonacoEnvironment.getWorkerUrl` shim that webpack/Vite hide; raw script load is fragile | Zero workers — runs on the main thread |
| Self-hosting cost on a 10 MB-budget WASM page | The 1.3 MB sits **before** the WASM payload, so cold load becomes editor-blocking | Editor weight is small enough to ship from the same `wwwroot/lib/` as the framework |
| Modular / tree-shakable | Partial — the AMD loader pulls full editor bundle | First-class — only the extensions actually used (`history`, `lineNumbers`, `searchKeymap`, `sql`) get bundled |
| License | MIT | MIT |

Monaco's strengths (rich language services, inline diagnostics widgets, the same keybindings VS Code users already know) **do not** transfer to a CDN-loaded standalone script as cleanly as the marketing implies — the parts that make Monaco feel like VS Code (the language-services orchestration, the diff view, the multi-cursor command palette) require either the full `monaco-editor` UMD bundle or a worker harness. We get most of that with smaller CM6 extensions, and the SQL highlight + completion surface is already shipped by `@codemirror/lang-sql`.

## What CodeMirror 6 gives us out of the box

- `@codemirror/lang-sql` — TSQL highlighting, smart indent, bracket matching, snippet expansion API
- `@codemirror/autocomplete` — completion popup driven by an async source (our IntelliSense will register one in M3)
- `@codemirror/lint` — gutter markers + tooltips driven by an async source (our analyser surfaces findings here in T045/T046)
- `@codemirror/search` — `Ctrl+F` find/replace
- `@codemirror/state` — immutable doc model that makes IPC round-trips trivial (we serialise `state.doc.toString()`)
- A small JS interop surface (`SetText`, `GetText`, `SetSelection`, `GotoLine`, `OnTextChanged`) is enough for the M2 surface

## Trade-offs we accept

1. **Keybinding learning curve.** VS Code users will need to adjust to CM6's default chord set (most overlap, but `Ctrl+D` is "select next occurrence" in VS Code vs. "delete line" in CM6). We mitigate by binding the formatter / analyser actions to `Ctrl+K, Ctrl+F` and `Ctrl+K, Ctrl+L` chords that match the IDE plugin.
2. **No built-in DiffEditor.** We don't ship a side-by-side diff in M2; the format-preview diff lands in M3+ via a small custom view.
3. **Snippet syntax is CM-flavoured.** Our `.akmlsnippet` format already uses VS-flavoured placeholders (`$1`, `${1:default}`); the CM expansion API consumes the same syntax with a one-line adapter.

## How CM6 ships in the page

We **bundle** CM6 via the official ESM CDN (`https://esm.sh/...`) for the M2 dev loop and switch to a vendored copy under `wwwroot/lib/codemirror/` for the released build (T054 bundle-size audit will lock the version). The Blazor side is unaware: it talks to the JS shim in `wwwroot/js/akml-editor.js`.

## Reference implementation

- `src/AkmlSql.Web/wwwroot/js/akml-editor.js` — CM6 wrapper exposing the Blazor-facing API.
- `src/AkmlSql.Web/Shared/EditorComponent.razor` — Blazor wrapper that creates the editor on first render and forwards `SetText` / `GetText` / `OnTextChanged`.
- `src/AkmlSql.Web/Pages/Editor.razor` — the host page wiring formatter, analyser, and the problems-list side panel.
